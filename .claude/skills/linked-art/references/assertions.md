## The rule Linked Art sets itself

Current knowledge goes in the plain pattern; history and context are layered on with
`AttributeAssignment` only when necessary. "The use of context specific assertions or
other attribute assignments should be kept to a minimum if possible. The data structure
is significantly more complex… This pattern should only be used if there is no other way
to express the knowledge."

## AttributeAssignment

An `Activity` (typically by a curator or researcher) that assigns a value to an entity.
It has the usual `carried_out_by`, `timespan` (when the assignment was made, not how long
it was believed), `took_place_at`.

- **Subject side:** the entity has `attributed_by` → the assignment, which has
  `assigned_property` (e.g. `"made_of"`, `"carried_out_by"`, `"part"`) and `assigned`
  (the value). Subject, predicate, object — a reified triple.
- **Value side:** when the value is what needs context, the value has `assigned_by` → the
  assignment, e.g. two accession numbers for one jointly owned object, each assigned by
  its own museum.
- **Source of knowledge:** `used_specific_object` → the database, book or object the
  information came from (an entity, not a string). A citation string goes in a statement
  (`referred_to_by`) on the assignment.

## Patterns built on it

| Case | Pattern |
|---|---|
| **Possibly by / attributed to** | `attributed_by` on the `Production`; the assignment is classified *Possibly By* (aat:300404272), `assigned_property` `"part"`, `assigned` a `Production` carried out by the artist |
| **Former attribution** | the same shape, for what was previously believed; the main `carried_out_by` is the current view |
| **Context-specific** (an exhibition's own title or number for an object) | `attributed_by` with `caused_by` → the exhibition activity |
| **Related, nature unknown** ("related objects") | an assignment with `assigned` the other entity and a Display Name; "a last resort" |
| **Relationships the model doesn't have** (student of, teacher of) | an assignment with `assigned` the other person and a Display Name ("Student Of"). Linked Art says these social relationships are "too many… to model them all separately"; modelling them as joining a Group is possible but heavy |
| **Credit for an embedded statement** | `created_by` on the statement, as if it were a full text record |
| **AI-generated content** | classify the statement *AI Generated Content* (aat:300456841), or give its `Creation` the technique aat:300456842 |

## The limit that shaped D53

> "this pattern does not allow for individual relationships to be flagged as being
> generated by an AI. For example, if software extracted the list of materials from a
> statement and created a series of `made_of` references… these links cannot be reified
> to add the creation information, just as they cannot be reified to add a human who
> asserted the relationship. The use of `AttributeAssignment`, as above, is possible but
> not encouraged."

Placard needs exactly that for every link: which source, when retrieved, how confident,
who verified, what it superseded (§4.7, constraint 2). Linked Art leaves it to a heavy
pattern it discourages, so the claim envelope is Placard's own and the vocabulary sits
inside it (D53). Placard's OCR-extracted materials, for instance, are the case quoted
above.

**In projections:** when a Linked Art document is generated from claims, the current
view goes in the plain properties; a contested or former attribution can be emitted as
`AttributeAssignment` where it matters to the reader (an "attributed to" qualifier
always does). Confidence and supersession history stay in the claims.
